9. Profile Schema Expansion & Field Persistence (Experience, Education, Job Preferences)
Date: 2026-10-27
======================================================================

1. Root Cause Analysis:
   - In Mongoose, schemas have `strict: true` by default. Any field not explicitly declared in `UserSchema` is automatically and silently stripped upon `findOneAndUpdate` and `save`.
   - `UserSchema` previously lacked definitions for candidate work experiences, education history, job preferences (desired role, work mode, preferred locations, expected compensation, employment type, notice period), professional headline (`title`/`headline`), location, bio, and social links.
   - Consequently, when mobile clients or frontend users saved these fields via `POST /api/user/updateUserFields`, MongoDB dropped them. Upon subsequent `GET /api/user/profile` calls, the fields returned empty/undefined.

2. Model Schema Expansion (`src/models/userModel.js`):
   - Added explicit typed schema definitions for:
     * `experienceDetails`, `experienceHistory`, `workExperience`: Array of work experiences (role, company, startDate, endDate, isCurrent, location, description).
     * `educationDetails`, `educationHistory`: Array of education entries (institution, degree, field, startYear, endYear, location).
     * `desiredRole`, `preferredRole`: Desired role preferences.
     * `workMode`, `preferredWorkMode`, `workModes`: Multi-select work mode options (Remote, Hybrid, Onsite).
     * `preferredLocations`, `preferredLocation`: Preferred geographical hubs.
     * `expectedSalary`, `salary`: Candidate compensation expectations.
     * `employmentType`: Employment type preferences (Full-time, Contract, Internship, Part-time).
     * `noticePeriod`: Candidate availability timeframe.
     * `fullName`, `title`, `headline`, `location`, `bio`: Personal identity & headline.
     * `portfolioUrl`, `linkedinUrl`, `githubUrl`: Portfolio and external profile links.
     * `recruiterViews`, `openToOffers`: Recruiter visibility and engagement counters.
   - Enabled `{ strict: false }` on `UserSchema` to ensure forward compatibility with any future candidate attributes without field truncation.

3. Controller Enhancements (`src/controllers/userController.js`):
   - In `updateUserFields`:
     * User identification now seamlessly falls back to `req.user?._id` or `req.user?.email` from the authenticated JWT session if not explicitly provided in `req.body.document`.
     * Implemented automatic bidirectional syncing for aliases:
       - `experienceDetails` <-> `workExperience` <-> `experienceHistory`
       - `educationDetails` <-> `educationHistory`
       - `title` <-> `headline` <-> `role`
       - `desiredRole` <-> `preferredRole` <-> `role`
       - `workMode` <-> `preferredWorkMode` <-> `workModes`
       - `preferredLocations` <-> `preferredLocation`
       - `expectedSalary` <-> `salary`
       - `fullName` <-> `firstName` + `lastName`
     * Switched update execution to atomic `{ $set: updateData }` using `findOneAndUpdate(filter, { $set: updateData }, { new: true, runValidators: false })`.
   - In `getProfileDetails`:
     * Returns a lean plain document (`.lean()`) with alias mappings guaranteed, ensuring mobile and web clients retrieve all fields consistently regardless of which alias key they query.

16. SAVED JOBS END-TO-END RELIABILITY FIX
Date: 2026-10-28
Context: Mobile Home, Job Details, Saved Jobs tab, Profile count, and backend saved-job APIs

1. Root causes identified:
   - The mobile Saved Jobs tab requested only page 1 with `pageSize: 50`, so any later pages were never shown.
   - `GET /api/getSavedJobs` filtered saved records to `status: "ACTIVE"` and `positions > 0`. Jobs disappeared from Saved Jobs as soon as they were closed, deactivated, or filled, even though the user's saved record still existed.
   - Saved jobs were sorted by the job posting creation date instead of the date the user saved them.
   - Saved-job endpoints trusted a request-supplied `userId` instead of consistently using the authenticated Passport user, allowing ownership mismatches.
   - Home/Jobs card bookmark state lived inside each card. Duplicate representations of the same job (featured and recent) could show different bookmark states, and refreshed job props did not reliably update local state.
   - The Saved tab optimistically removed a job but did not restore it when the backend unsave request failed.

2. Backend fixes (`src/controllers/jobsController.js`):
   - `upsertSavedJob` now derives ownership from `req.user._id`, rejects a mismatched supplied user ID with HTTP 403, validates `jobId` and `isSaved`, and rejects attempts to save missing jobs.
   - Re-saving updates the saved timestamp so "Recently saved" reflects the user's actual action.
   - Legacy duplicate records for the same user/job pair are removed after a successful upsert.
   - Job-feed/detail bookmark checks now look specifically for an `isSaved: true` record, so a legacy duplicate false record cannot hide a valid saved state.
   - `getSavedJobs` and legacy `getSavedJobsByUserId` now enforce authenticated ownership.
   - Removed the ACTIVE-status and positive-position restrictions from saved-job retrieval. Every still-existing saved job is returned, including inactive/closed roles.
   - Deduplicated legacy saved entries, ignored invalid/stale job IDs safely, ordered results by saved timestamp, retained existing web filter support, and capped individual API pages at 100.
   - Added `savedAt` to each result and `totalCount` to the response while preserving pagination.
   - Replaced raw database error-object responses with stable client-safe failure messages.

3. Mobile fixes (`hireinsecondmobile`):
   - Added `getAllSavedJobs` in `src/api/jobs.ts` to request every saved-job page and deduplicate results before rendering.
   - Updated `src/app/(tabs)/saved.tsx` to load all pages on focus, report load failures, use the real saved timestamp, and restore an optimistically removed item if unsaving fails.
   - Closed/deactivated/filled saved roles remain visible as requested, display an "Applications closed" state, and cannot launch the apply flow.
   - Updated `JobCard` and `FeaturedJobCard` to use parent-controlled bookmark state, keeping Home featured/recent cards and the Jobs tab synchronized. Duplicate taps are blocked while save requests are pending, with optimistic state rolled back on failure.
   - Updated Job Details to block duplicate save requests and to show a disabled "Applications Closed" action for closed saved roles.
   - Updated the Profile saved count to use backend `totalCount` instead of the length of only the first page.
   - Added the approved design record at `docs/superpowers/specs/2026-10-28-saved-jobs-fix-design.md`.

4. Automated verification:
   - Added `src/controllers/jobsController.test.js` using Node's built-in test runner.
   - `npm test`: 2/2 backend tests passed (cross-user write rejection; closed saved-role retrieval with saved timestamp).
   - `node --check src/controllers/jobsController.js`: passed.
   - `node --check src/controllers/jobsController.test.js`: passed.
   - `npx tsc --noEmit`: passed with zero TypeScript errors.
   - `npx expo lint`: passed with zero errors. Two pre-existing warnings remain in `src/api/client.ts` and `src/lib/googleAuth.ts`; neither is related to saved jobs.
   - `git diff --check`: passed in both mobile and backend repositories.

5. Compatibility and data notes:
   - Existing request payloads may continue sending `userId`, but it must match the authenticated account.
   - Existing web saved-job keyword/filter/pagination behavior was retained.
   - No dependency or database migration was added. Legacy duplicates are repaired opportunistically the next time that user/job save state is updated.
   - Existing unrelated urgency/requisition edits already present in `jobsController.js`, `jobsModel.js`, and earlier `Update.txt` sections were preserved.
